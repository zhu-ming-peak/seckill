# 阶段 E 固定测试方案

制定：2026-10-30，正式运行前固定。对象为三个本地 Git 标签的原始源码构建，不改业务实现。

## 目标与边界

分别验证业务正确性、查询接口性能、固定批量下单的响应与完成时间。不得把 202 当成成功订单，也不预设 Redis 或 MQ 一定更快。本机施压与服务共用 Windows/WSL，不能由此推导 ECS、云数据库或生产容量。

- v0.1.0-db（b7463d5）、v0.2.0-cache（b73bd05）、v0.3.0-async（e199b42）。
- 按标签导出独立副本，重跑各自原有测试并构建，记录提交与 JAR SHA-256。当前工作树不切换。

## 场景

| 场景 | 条件 | 记录 |
| --- | --- | --- |
| 功能矩阵 | 每版本执行正常、重试、重复购买、他人查询、无效活动、参数错误 | 状态码与业务断言 |
| 超额抢购 | 32 请求、16 并发、8 份库存、不同用户 | 8 成功、24 售罄、无超卖 |
| 同用户并发 | 16 请求、16 并发、8 份库存、同一用户不同编号 | 仅 1 份资格及订单 |
| 活动查询 | GET /api/activities/{id}；并发 1/8/16；每档 4 秒 | 全部延迟、实际响应 RPS、错误与资源 |
| 固定批量下单 | 每轮新活动、128 库存、128 不同用户；并发 1/8/16 | 受理/响应延迟与 RPS、已提交订单观察延迟和完成吞吐 |
| 冷/热缓存 | 缓存版商品接口；每轮 MISS/HIT 各 100 次，随机交错 | X-Product-Cache 断言、延迟分布；不报告冷缓存 RPS |

每个性能条件重复 3 轮，版本顺序依次 DB→Cache→Async、Cache→Async→DB、Async→DB→Cache；并发档位也随重复轮次轮换。缓存 MISS 前仅删除本轮商品键，HIT 前在计时外填充；控制操作不计入请求延迟。

## 指标口径

- 实际工具：Python 闭环 HTTP 施压器，固定线程/连接数、每工作线程顺序请求并复用连接；没有目标开放到达率，也不消除闭环等待偏差。
- 响应延迟：perf_counter，从 HTTP 请求开始到完整响应解析完成；含每线程首个连接的建立耗时。
- 响应吞吐：实际响应数/整轮从启动到最后响应的墙钟时长，包含尾部请求。
- 业务完成：独立只读数据库连接每约 100 ms 查询新订单，第一次可见代表事务已经提交。所有版本同样观察；这是含轮询及查询时间的上界，不能用于分辨低于观察粒度的提交差异。
- 异步受理与完成分别记。固定批次完成吞吐 = 成功订单数/从批次开始到最后订单首次可见的时长，不是稳态最大处理能力。
- HTTP 2xx、业务资格数、最终成功订单数分开；409 预期拒绝不混入未知系统故障。5xx/网络异常单列，发生时保留原始轮次。
- 完成后核对初始 = 数据库剩余 + 订单；异步 ACCEPTED/PENDING 清零后再比较 Redis。Redis 修复等待与订单完成时间分开。
- 资源每约 200 ms 采样：应用、MySQL、施压器 CPU 累计时间和 RSS；主机 CPU、可用内存。进程 CPU 以单核 100% 为口径，可超过 100%。不声称单个应用 CPU 代表 WSL Broker/Redis 的全部成本。
- 重复轮次只有 n=3，展示全部点及中位数/范围，不做显著性检验或伪造置信区间；原始请求不能当作独立机器重复实验。

## PTS 学习记录

PTS 虚拟用户模式侧重并发业务会话，RPS 模式配置每秒请求数；本次闭环线程场景更接近固定并发压力，不等同于给定 RPS。见[官方压力模型](https://help.aliyun.com/zh/pts/performance-test-pts-3-0/user-guide/pressure-model)。

使用流程：准备目标与测试数据 → 定义 API/业务会话 → 设置请求数据和业务断言 → 设置压力模式、持续时间及压力来源 → 试请求 → 运行并观察 → 导出报告、采样明细和环境条件。平台报告区分请求成功率与业务断言成功率，提供响应时间、吞吐、错误与施压机资源信息。异步秒杀应对 SUCCESS/订单另设检查，不能仅断言 HTTP 202。见[官方报告说明](https://www.alibabacloud.com/help/zh/pts/performance-test-pts-3-0/user-guide/check-pts-3-report)。
